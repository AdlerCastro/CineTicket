**Última atualização:** 24/08 — Backend Agent: **Risco #11 (D58) fechado — `POST /auth/refresh` implementado, escopo expandido durante a tarefa para incluir `POST /auth/logout` real (autorizado explicitamente pelo usuário).** Branch `feature/sprint-5-token-refresh`.

**Achados confirmados antes de implementar (pedido explícito da tarefa — "confirme o estado real, não presuma")**: (1) `User.refreshTokenHash` era campo morto — existia no schema e era excluído de toda resposta (`sanitizeUser`), mas nada em `login`/`register` jamais escrevia nele; sempre `null`. (2) Não existia `logout` nenhum no backend (`grep` por "logout" em `src`/`test` não retornava nada) — `useAuth.tsx` do frontend só limpa estado local/`localStorage`, nunca chama a API. Ou seja, o cookie httpOnly de refresh nunca era invalidado no servidor, só ficava para trás no navegador até expirar sozinho em 7 dias. (3) Não havia `cookie-parser` instalado nem `req.cookies` usado em lugar nenhum — só `res.cookie()` pra setar.

**Consequência do achado (1) pro desenho**: implementar `/auth/refresh` "validando contra `User.refreshTokenHash`" como pedido exigia primeiro tornar esse campo vivo — `login`/`register` (refatorados para um `issueTokens()` privado comum) agora gravam o hash de verdade a cada emissão de tokens. Isso muda o risco original de D58 (achado (1) era inofensivo por ser morto) — a partir desta tarefa o hash é ativo e teria ficado inconsistente com um logout que só limpa estado local. Por isso o escopo foi expandido a pedido do usuário para incluir `POST /auth/logout` de verdade (zera `refreshTokenHash` + `res.clearCookie`), em vez de deixar um endpoint de refresh "meio pronto" sem forma real de invalidar sessão.

**Decisões de desenho**: (a) **Rotação do refresh token a cada uso** (novo token + novo hash substituindo o anterior) — mais seguro que reemitir o mesmo, custo extra desprezível já que um novo par de tokens precisa ser assinado de qualquer forma. Achado real durante os testes: sem um claim `jti` aleatório, dois `jwtService.sign()` com o mesmo payload dentro do mesmo segundo (`iat` com resolução de 1s) produzem o token **byte-a-byte idêntico** — a rotação virava um no-op silencioso quando `/auth/refresh` era chamado duas vezes rápido o bastante. Corrigido adicionando `jti: randomUUID()` a todo token assinado (access e refresh). (b) **Hash do refresh token via SHA-256, não bcrypt** — bcrypt trunca o input em 72 bytes, mais curto que um JWT típico; dois refresh tokens do mesmo usuário podem compartilhar header+payload e colidir num `bcrypt.compare` falso-positivo. O token já carrega entropia criptográfica própria (é assinado), então o hash lento do bcrypt (pensado pra senha de baixa entropia) não agrega nada aqui — comparação feita com `timingSafeEqual`. (c) **`cookie-parser` instalado e registrado em `main.ts`** (`app.use(cookieParser())`) — autorizado explicitamente pelo usuário a tocar `main.ts` nesta tarefa (normalmente fora do escopo de "auth puro"); `test/e2e/support/test-app.ts` replicou o mesmo `app.use(cookieParser())`, já que o bootstrap de teste não passa por `main.ts#bootstrap()`. (d) **`POST /auth/logout` sem guard** — precisa funcionar mesmo com access token já expirado (cenário comum: sessão ociosa, usuário clica em sair); verifica a assinatura do refresh token com `ignoreExpiration: true` antes de confiar no `sub` (evita que um cookie forjado zere o hash de outro usuário) e é idempotente — sem cookie, ou com assinatura inválida, ainda retorna 200 (cookie é limpo de qualquer forma), sem 401/500.

**Frontend ainda não chama `/auth/logout`** (fora do escopo desta tarefa, próxima sessão) — `useAuth.tsx` continua só limpando estado local. Até essa integração acontecer, o comportamento visível pro usuário não muda (a UI já "desloga" na hora), mas o cookie/hash do servidor só é invalidado de verdade quando o frontend passar a chamar o endpoint novo.

Teste novo `test/e2e/auth-refresh.e2e-spec.ts` (14 casos, dois `describe`): `POST /auth/refresh` — login grava hash real; refresh válido emite access token novo e funcional numa rota protegida real (`GET /tickets/mine`); rotação confirmada (cookie antigo rejeitado após uma segunda chamada); sem cookie, assinatura inválida, secret errado, token expirado e usuário inexistente → 401 em todos, nunca 500. `POST /auth/logout` — zera `refreshTokenHash` no banco (não só a resposta HTTP); `Set-Cookie` limpo (`refreshToken=;`); **critério de pronto explícito da tarefa**: refresh usado depois de logout → 401 (hash zerado, não bate mais); idempotente sem cookie/com cookie inválido (200 nos dois casos); login funciona normalmente depois de um logout, sem regressão. Usuários descartáveis por teste (não o `CUSTOMER1_EMAIL` fixo do seed) — com Jest rodando arquivos de spec em paralelo por padrão (sem `--runInBand`), um usuário fixo compartilhado com outras specs que também logam como `CUSTOMER1` criaria corrida real entre workers nas asserções de estado exato de `refreshTokenHash`; descartável por teste elimina a contaminação cruzada. `lint`/`build`/`test:e2e` (18 suítes, 86 testes — os 72 anteriores + 14 novos) limpos, suíte completa revalidada sem regressão (login/register/todas as jornadas).
